## Детальное описание рисков

### R-029 — Session management — нет idle timeout

**Категория:** Безопасность | **Критичность:** Средняя | **Статус:** 🟡 Мониторинг

**Описание:** T2307 реализовал absolute timeout 24 часа (SessionStore TTL). Idle timeout не реализован — сессия живёт 24 часа даже без активности.

**Влияние:** При краже сессионного cookie → доступ до 24 часов.

**Митигация:**
- ✅ Absolute timeout: 24 часа (реализовано в T2307, SessionStore TTL)
- ⏳ Idle timeout: 30 мин без активности → require re-auth (отложено)
- ⏳ Session rotation при изменении UA/IP (отложено)

**Источник:** 152-ФЗ, безопасность.md §12, T2307

### R-041 — Graceful migration: старые сессии с ID Token → 401

**Категория:** Безопасность | **Критичность:** Низкая | **Статус:** 🟢 Принят

**Описание:** T2307 заменил ID Token в cookie на random hex session token. Старые cookie содержат JWT, который не найден в Redis по ключу `lkfl:sess:eyJhb...`.

**Влияние:** Пользователь с действующей сессией увидит 401 → redirect /login → silent re-login через Keycloak SSO (без ввода пароля).

**Митигация:**
- Не требуется миграционный код — cookie истечёт по MaxAge (24ч) или при следующем запросе
- Silent re-login через Keycloak SSO — UX-воздействие минимально

**Источник:** T2307

### R-042 — Keycloak SSO инвалидация при logout

**Категория:** Безопасность | **Критичность:** Средняя | **Статус:** ✅ Закрыт

**Описание:** При logout нужно инвалидировать Keycloak SSO сессию, чтобы пользователь не мог автоматически перезайти.

**Решение (T2308):** Browser-based logout через redirect.

Поток:
1. Frontend: `window.location.href = '/api/v1/auth/logout'`
2. Backend: удаляет session (Redis) + token + cookie → 302 → Keycloak logout endpoint
3. Keycloak: инвалидирует SSO сессию + удаляет `KAUTH_SESSION_ID` cookie → 302 → `/login`

**Почему это работает:**
- Browser-based logout — единственный надёжный способ инвалидации SSO
- Server-side подходы (Admin API, POST Bearer) не удаляют `KAUTH_SESSION_ID` cookie браузера
- Keycloak logout endpoint удаляет все SSO cookie и инвалидирует сессию на стороне IdP

**Верификация:**
- ✅ E2E тест подтверждает: logout → повторный вход требует ввода логина/пароля
- ✅ `KAUTH_SESSION_ID` cookie удалена после logout
- ✅ `lkfl_session` cookie удалена после logout
- ✅ localStorage очищен после logout
- ✅ Server-side code (`invalidateKeycloakSSO`, `getAdminToken`, `fetchAdmin`) удалён (~185 строк)

**Источник:** T2307, `internal/auth/handler.go:invalidateKeycloakSSO`

### R-043 — SameSite=None cookie без HTTPS в dev

**Категория:** Безопасность | **Критичность:** Низкая | **Статус:** ✅ Закрыт

**Описание:** Cookie с `SameSite=None` требует `Secure=true`. Браузеры игнорируют cookie если `Secure=false` при `SameSite=None`.

**Решение (T2307):**
- Production (`isSecure=true`): `SameSite=None, Secure=true` → работает
- Development (`isSecure=false`): `SameSite=Lax, Secure=false` → работает
- Startup log предупреждает о конфигурации (`LogStartupWarnings`)

**Митигация:**
- ✅ Lax fallback для localhost
- ✅ None только при `isSecure=true`
- ✅ Startup validation log в `LogStartupWarnings()`
- ✅ `COOKIE_DOMAIN` в config (не просто `os.Getenv`)

**Источник:** T2307, `internal/auth/handler.go:setSessionCookie`

## Процесс управления рисками

### Когда добавлять риск

1. **Аудит реализации** (hardening, milestone review) — как в M22
2. **Code review** — обнаружение уязвимости/проблемы
3. **ADR** — новый архитектурный риск при принятии решения
4. **Incident postmortem** — риск, приведший к инциденту
5. **Penetration test** — найденные уязвимости
6. **Dependency update** — CVE в зависимости

### Формат нового риска

```markdown
### R-{NNN} — {Название}

**Категория:** {Безопасность | Надёжность | Архитектура | Совместимость | Комплаенс | Performance}
**Критичность:** {Критическая | Высокая | Средняя | Низкая | Информация}
**Статус:** {🔴 Открыт | 🟡 Мониторинг | 🟢 Принят | ✅ Закрыт | ⛔ Не актуален}

**Описание:** {Что за риск и почему он важен}
**Влияние:** {Что произойдёт, если риск реализуется}
**Митигация:** {Как снизить/устранить риск}
**Источник:** {Где обнаружен: аудит M22, ADR-035, пентест и т.д.}
```

### Пересмотр рисков

- **Ежемесячно:** архитектор проверяет статус открытых/мониторинга рисков
- **При завершении вехи:** все риски из audit отчёта добавлены в реестр
- **При изменении архитектуры:** проверить актуальность существующих рисков
